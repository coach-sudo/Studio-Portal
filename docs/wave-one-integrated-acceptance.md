## Findings and disposition

**Release blockers**

- B1: Dedicated persistent staging database, service/browser configuration and access protection are absent or unverified. Approve and configure a non-production target before deployment.
- B2: Real sandbox Stripe/webhook, isolated Google Calendar and email sink acceptance are incomplete. Obtain legitimate isolated credentials and exercise relevant retries/suppression; document any explicit product-owner waiver, never silently count blocked checks as passed.
- B3: All six implementation PRs remain drafts; integration review and production release are unapproved. Main rules require no approving review and allow skipped smoke. Obtain explicit review approval and a genuinely exercised staging/health gate before merge/publication.
- B4: Fresh acceptance-specific upgrade, expanded role and both-query-mode results must pass; pending runs cannot be waived by previous PR results.

**Significant non-blocking risks**

- Legacy dollar-adjustment mutation/audit has no durable replay receipt: verify history after an ambiguous reply; do not blindly retry or reconcile as rollback.
- Bulk non-FK fencing/reference scans need production-sized staging latency/lock review. Review capped at 5,000; processing is bounded and five-minute cadence can require many invocations.
- In-flight remote calendar requests cannot be rolled back with PostgreSQL; latest projection recovery is observable but not atomic external delivery.
- Broad legacy/global activity reads and a 23,090-byte CSS gzip warning remain; hard 130KB JS/25KB CSS budgets pass at the implementation checkpoint.
- Import identity/participation multi-call boundaries rely on recovery sweep; activation evidence is unverified; mobile long-name/tab discoverability and operational history retention need continued review.

**Future improvements**: Wave 2 navigation/search/selected-student consistency, later materials/workspace/operations waves, full product accessibility/WebKit. Preserve their approved scope; no implementation is started here.

## Rollback and forward recovery

Revert or republish the **last verified compatible integrated application/functions** only under release authorization. Keep additive schemas, receipts, deletion snapshots, audit and append-only ledger history. Reverting the app cannot undo a valid debit, cancellation or physical deletion; disabling automatic use preserves holds and is not a universal rollback switch. Do not replay stale workers against newly changed records without their version/claim checks.

If failures occur, capture job/receipt IDs and safe error metadata, stop new destructive approvals, and use existing retry/backoff/lease recovery after fixing the cause. Completed items are not rerun as new operations; stale dependency/version conflicts require fresh review. For interrupted migrations inspect the actual applied prefix, correct forward in a reviewed migration and repeat isolated rehearsal before authorization. Never suggest deleting ledger rows, reversing legitimate payment history or destructive down-migrations. Financial ambiguity goes to explicit reconciliation review; it is not automatically repaired during acceptance or rollback.
