# Stripe booking installment settlement

Before implementation: B06/B07/B09, X04/X06/X13/X20. Keep signed webhook verification, append-only payments, existing first-booking confirmation/credit logic, and installment pricing/count policy. A new invoice-identity transaction must commit booking, ledger, audit, replay receipt and durable provider/notification intent together. Provider retries must not reapply money. Existing historical discrepancies require reviewed reconciliation, not an automatic balance rewrite. Rollback retains receipts and intents; do not return to the legacy increment path after accepting new receipts.

Reproduced with synthetic DB/Stripe boundaries: a cancellation outage after the second installment commits paid=12000/count=2; identical-event retry changes paid=18000/count=3 while the ledger has one 6000 invoice entry. This is not evidence of a production discrepancy. Keep the original reproduction as an investigation artifact and add corrected failure/retry/concurrency coverage.

Provider rules were verified with Stripe CLI 1.55.3: [API v1 idempotency](https://docs.stripe.com/api/idempotent_requests) permits pruning after 24 hours; [webhooks](https://docs.stripe.com/webhooks#handle-duplicate-events) can deliver separate events for one invoice. Database identity therefore uses invoice ID, and unknown provider outcomes cannot be blindly recreated beyond the idempotency window. No real provider writes or live webhook delivery are authorized.

Release gates: isolated PostgreSQL payment/audit/intent fault injection and concurrency; synthetic first-payment/renewal/provider faults; then approved Stripe sandbox and authenticated downstream acceptance. The Stripe connector currently requires reauthentication. Package renewals, recurring-series allocation, invitation recovery and other webhook branches remain separately unverified. No existing balance or ledger may be repaired automatically.

Implemented: invoice-ID request hash/receipt, same-studio serialization and student/booking row locks; first-invoice confirmation inside the transaction; checked ledger/audit/intent insertion; leased provider/notification recovery; fixed rounding idempotency identity; cancellation state reconciliation; checked webhook acknowledgement. Unknown rounding outcomes after 23 hours are held for review rather than recreated after provider idempotency retention may expire. No new background worker is enabled: Stripe redelivery drives retries, and exhausted deliveries retain the private recovery intent for an approved runbook.

Local evidence: 11 targeted tests across two files passed, including provider failure, same/different event replay, lost committed response, failed ledger, failed acknowledgement, failed notification queue, fixed rounding key and unknown-outcome hold, and already-cancelled provider state. TypeScript passed. The original defect fixture is retained as `.ts.txt`; it is evidence of the old bug, not a passing regression. PostgreSQL tests and the named-container concurrency script must execute in CI; local Windows container access remains unavailable.

Policy/release holds: zero-value installment invoices, payments against cancelled/completed bookings, and pre-cutover invoices with possible partial writes require reconciliation instead of automatic counter changes. Review these paths before release; this draft must not be used as a balance-repair or historical-backfill command. Initial portal invitation recovery still depends on the existing account-provisioning implementation.
