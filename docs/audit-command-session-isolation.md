# Studio command session and request isolation

Before implementation: investigate the shared frontend command in-flight map against A03 (account sign-in/recovery and logout cache isolation), A04 (guardian/dependent permission revocation), B08/B10 (lesson commands), D05/D06 (financial commands), F07 (security/recovery), and X06/X09/X10/X18 (scheduling/financial commands, account scope and provider review retries). These are affected acceptance inventories, not end-to-end passes. This is a client request-boundary change, not a new server permission or financial policy.

The existing map keys only domain/command/entity ID/payload. They omit authentication, entity type, version, reason, next status and explicit idempotency key. First reproduce a delayed request with synthetic account switching and changed command metadata. If confirmed, capture the authentication session once, scope in-flight requests to that session and the complete serialized command envelope, and send the exact captured token/envelope. Preserve concurrent identical calls without an explicit key as one logical request. Different explicit keys must reach the server separately. Keep failures retryable and entries removable.

Dependencies: none; independently reviewable against audited main. Rollback implication: restoring the old client restores unsafe coalescing; no database migration or data repair is involved. Server authorization, RLS, optimistic version checks and durable idempotency remain authoritative. Synthetic responses do not establish hosted authorization or that any real student's data was exposed. Do not include tokens in logs, errors or evidence.

## Evidence and change

**SEC-R01 is reproduced** at the audited main baseline. Two retained synthetic tests demonstrate (1) a new student session receiving the previous coach call's delayed result without issuing its own authenticated request, and (2) changed version/reason/next-status/retry-key metadata receiving the first call's response. Both reproductions passed against the old implementation; the exact test source and log are retained in `audit-command-session/evidence/`. No provider or database was contacted. This does not establish a historical real-user disclosure.

The implementation snapshots the serialized command before awaiting authentication, captures the session once, and scopes the in-flight map by captured principal/token, domain and complete wire envelope. Execution uses that captured token/envelope. Identical simultaneous calls retain one wire request and one generated key; different explicit keys or metadata reach the server independently. Completed and failed requests release their entry. A refreshed token has a separate request scope. Durable replay still requires a caller-retained key; this short-lived map is not durable idempotency.

**21 new command-boundary tests plus four existing identity/error tests pass (25 total)**. Coverage includes account switch, sign-out, token refresh, delayed auth/input edits, all previously omitted metadata, explicit-key conflict delegation, network/HTTP failures and recovery, old-session cleanup and completed-call cache release. TypeScript passes. Full exact-head CI and final combined-candidate/browser account-switch acceptance remain required. Production Auth compromised-password protection is a separate SP-18 proposal and remains disabled at the last read-only observation.
