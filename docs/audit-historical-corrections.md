# Audited existing-record date/time corrections (SP-04)

Preimplementation scope: B04/B08/B10, D03/D05/D06, C05/C06 and X01/X02/X05/X06/X08/X13/X19/X20. Depends on #73's explicit zoned controls and #71's atomic manual creation. The user approved the separate correction policy in the central decisions document on October 28; no release or hosted mutation is approved.

Use an exact occurrence/version, reason and immutable replay identity. Preserve original creation time, attendance, participant identity, notes/work and append-only accounting. Preview financial/checkout/credit/Calendar/series dependencies and compare a sealed fingerprint under locks at execution. Financial dependencies require explicit acknowledgement and remain visibly flagged for review. In-flight checkout blocks correction. Update a sole linked booking's dates consistently; a shared series booking retains its aggregate anchor, which is identified in preview. No implicit series edit, charge/refund, repricing, credit allocation/reversal or notification.

Automatic coverage must skip corrected records until explicit financial handling; a date correction is not authority to consume a credit. Pending provider review blocks automatic date/outcome changes, and projection leases are fenced so a stale worker cannot project the correction. The UI must show the correction and financial/Calendar review holds, preserve input after failure and retry the same identity after a lost response. Existing upcoming reschedule keeps its separate policy.

Rollback retains additive correction receipts, review holds and recorded history. Do not revert to an application path that silently ignores a pending correction or invents financial/provider success. Require actual PostgreSQL role/fault/replay/booking/credit/provider-fencing/concurrency tests and Chromium/WebKit keyboard/accessibility/screenshot acceptance before review is complete. No whole-system or provider PASS is inferred from a unit test.

The database/API contract is reviewed separately from its interface. Six handler cases passed locally: all four guarded RPC routes, non-coach rejection, and propagation of transaction failure. Sealed dependencies include private checkout claims but those bodies are excluded from the public preview response. The new private correction proof is bound to its PostgreSQL transaction and exact target dates; callers cannot fabricate it. Automatic source date/outcome updates to any corrected record require explicit coach authority, even after a coach records a review. Existing upcoming occurrence commands keep their verified coach context. Automatic credit allocation remains held; explicit manual credit commands retain their existing eligibility checks.

Current SQL and separate-session scripts are authored but not executed locally; isolated CI must actually validate them. No historical correction, ledger mutation, provider request or role mutation has been performed in a hosted environment. The interface and browser evidence will be a dependent draft.
