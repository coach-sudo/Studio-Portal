## Information hierarchy and workflows

Overview reads a coach-only, bounded `student_workspace_summary`: one exact upcoming lesson, latest coaching takeaway, at most five canonical resources and five practices, question/approval counts and financial exceptions. Goals/private context require disclosure. The coach's private takeaway never enters portal financial responses. The primary record sections are Overview, Lessons, My Work, Notes, Household and Payments. Account administration and Actor Page remain in the record menu with their existing URLs. Desktop exposes Add lesson and Write note, with an Assign menu for practice/resources and a separate Message action. Narrow screens use one Add menu and Message. Changing the student closes authoring state; private financial forms also remount for their owning identity/student.

Household defaults to identifiable contact rows with relationship, contact information, payer/scheduling responsibility, invitation delivery and portal access. Identity/responsibility editing is separate from expanded access controls. Manage Access opens the existing contact command form with permissions and notifications deliberately exposed. Sending to a delivery provider is not presented as account activation. Activation remains explicitly unverified; the current model has no authoritative first-access event. Existing minor restrictions, mandatory notification policy and access revocation remain server-controlled.

Payments starts with known financial obligations and separately labeled dollar credit, followed by remaining/available/reserved lesson credits. Unknown balances say Review required. Invoice-linked lessons are counted through issued invoices; shared bookings are counted once. Currency totals stay separate. Ambiguous invoice/shared-booking associations require review. Invoices, packages/history/adjustments, reminders and pricing/forecasts are secondary disclosures. An invoice URL opens its disclosure and exact existing dialog. Package and payment history have real page controls, and credit history is read in server pages of 25. Financial setup is no longer duplicated on Account. Dollar credits never silently reduce displayed obligations.

## Authoritative credits and refresh

The live credit panel reads #36's `student_credit_coverage`; frontend simulations are confined to the demo component. It shows covered and uncovered rows with actual reason codes, bounded pagination, automatic On/Off/Needs review, expired credits and recovery state. The enablement review uses the backend preview across the entire relevant set before pagination.

Settings saves and #37's applied/already-covered/skipped/failed outcomes are separate messages. A malformed response does not fabricate successful application. Manual Apply eligible credits now does not enable automatic use. During implementation, #37's account command was found to reject this action while automatic use was off. The additive migration uses the existing manual evaluator/allocator, retains manual recovery intent in the existing queue, and preserves receipt replay, lock order and audit. An explicit disable cancels queued manual intent. No competing allocator is introduced.

Mutation invalidation refreshes workspace/financial summaries and credit coverage. Recovery polls while pending; other active reads refresh every 30 seconds and on focus. Queries include actor/student identity. Credit forms remount on identity changes; failed authorized reads suppress cached previews. Credit history uses a guarded bounded RPC and excludes lesson logistics and free-form reasons from finance-only roles.

## Context and privacy

Next lesson opens the exact existing hub. Notes support exact note links; Today links to the intended lesson draft and reuses a matching draft. Practice links preserve its ID. Resource links validate resource, assignment and student together before using the existing resource detail component. Account and actor URLs remain compatible. No private file URLs are added to summary contracts.

The financial public facade remains invoker; its narrow private definer validates the same finance/minor/disabled-workspace predicate as credit diagnostics before aggregating totals independent of schedule RLS. It returns no topics, dates, lesson identities or note bodies. The coach summary/resource functions retain invoker RLS and explicit current-coach checks. Profile submissions remain private: a narrowly guarded helper returns only their approval count, without granting client table access. Student/guardian credit controls remain read-only.

## Workflow review

| Task                                | Default experience and retained advanced path                                                                                                                                     |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Understand the student              | Identity/focus, exact next lesson, latest takeaway, bounded canonical work and exceptions; goals/context behind disclosure                                                        |
| Identify household responsibilities | Contact rows show relationship, payer/scheduling and access separately; Edit contact preserves hidden permission defaults; Manage Access exposes the full protected controls      |
| Verify money and credits            | Known liabilities stay distinct from dollar credit and lesson credits; unknown liabilities say Review required; invoices and financial configuration remain directly discoverable |
| Enable and troubleshoot credit use  | Authoritative enable preview, Setting saved plus actual result counts, per-lesson reasons and observable recovery; manual use leaves the preference unchanged                     |
| Follow up after a lesson            | Today opens the exact lesson draft; repeated navigation/save reuses it; notes, practice and resources retain exact context                                                        |

The visual review checks the default hierarchy and the deliberately opened administration views. Automated success alone is not a claim of measured usability improvement or a substitute for the coordinated staging exercise.
