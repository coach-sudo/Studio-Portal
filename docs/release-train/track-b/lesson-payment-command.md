# Actual received-payment command — draft checkpoint

The legacy lesson payment action could reprice a lesson, change its paid total, and independently project a linked booking without inserting a ledger entry or checking the booking update result. This was a source-traced direct financial-integrity blocker; no hosted exploit was performed. The replacement records an explicit cash or bank amount already received against the original student and returns an immutable receipt. The two existing editor implementations share one component. The live calendar route opens the lesson workspace through its read-only drawer; the retained legacy LessonsView editor is also replaced but that editor is not reached through the current /coach/lessons redirect.

## Scope, dependencies and recovery

The new additive 20261029142227 migration depends on the existing B booking, historical correction and financial command migrations. It adds private lesson_ops.payment_receipts, a coach-authorized preview and record_lesson_payment command. Actor authorization is exact to the lesson studio and precedes receipt replay. The receipt key belongs to actor and studio; the complete normalized request is hashed. Identical replay returns the original immutable result, while changed payloads are rejected.

The command serializes its key, studio/calendar, original student, lesson, linked bookings and participants, then validates a sealed current context. It inserts the append-only payment entry before updating the booking and lesson with version checks. Audit and receipt creation are part of the same transaction. Any failure rolls back the ledger and projections. It changes neither price, original student, creation timestamp nor attendance, and queues no provider or notification effect. Refunds, waivers, repricing, invoices, existing credit attachments, shared/series/offering allocations, unexplained historical paid totals and provider-billed bookings are held for their reviewed journeys. Currency comes from the canonical booking or explicit studio setting, without an invented fallback.

Legacy set_payment_status calls now authorize the actor and return a review hold. An invoker trigger blocks raw anon/authenticated lesson monetary edits while retaining existing RLS and trusted service/definer invoice, credit, Stripe and payment commands. This is not a claim that all service-role financial paths use the new receipt. Existing provider/refund/checkout paths remain separate shared-system risks and external acceptance gates.

Pending requests are stored before sending in actor-scoped sessionStorage, retaining the exact request and key across reloads. Storage failure prevents the write. Recovery is offered even when a fresh context would now be paid or ineligible. Changing lessons clears the previous receipt UI. The backward-compatible studioCommand third expectedActorId argument checks the captured transport session before fetch, preventing an account switch from sending another actor's recovery envelope. Existing default callers, wire fields, request identity and in-flight/session semantics are preserved. The reusable guard is in 7c64498 + wording-only d6c3261.

The application and migration are one release unit: the UI requires both new RPCs, and the trigger intentionally stops old raw financial edits. This high-risk change must not be published before database, role and connected-flow acceptance. Once receipts exist, retain their schema and history; do not reverse the migration or delete accounting. Recovery uses the same command identity, and any financial correction requires a separately reviewed append-only command. A future rollback must hold affected UI writes while preserving committed records and RLS.
