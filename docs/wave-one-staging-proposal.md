4. Confirm a fresh anonymous browser cannot obtain HTML, assets, health/API responses, fixture responses or sensitive function responses on the site domain, deploy permalink and any alias. Record the actual gate response; do not assume a particular status code. Recheck after deployment. Keep protection enabled during recovery and cleanup.
5. The harness must obtain a short-lived perimeter session and carry it in **every browser context and API setup/teardown request**, while retaining the application's Bearer JWT. Current `e2e/global.setup.ts` does not implement this. Review that harness change before hosted automation. Do not introduce a Basic-Auth `Authorization` header that overwrites the application's Bearer header.

No access rule or deployment freeze has been applied during preparation. An authenticated dashboard review remains required; the read-only CLI result does not settle every publication control.

## Candidate-specific blockers and provider requirements

### Deployment context and trusted links

`netlify/functions/_shared/portal-url.ts` returns `https://portal.d-a-j.com` for **every `production` context**, including the staging site's current main deployment. Therefore do not publish this candidate to staging's production-context domain. `e2e-fixtures.ts` also rejects production context intentionally.

The proposed manual unpublished deploy uses CLI 27.8.0's `--context deploy-preview` for build environment selection, no `--prod` or `--prod-if-unlocked`. That flag alone is **not proof of runtime metadata**. Confirm generated release metadata, actual deploy context and trusted URL availability together. If Netlify cannot provide the required consistent metadata for an immutable manual deploy, stop and review an approved restricted Deploy Preview path or minimal staging-origin change; revalidate and re-pin any changed candidate. Do not falsify metadata to bypass production guards.

### Stripe sandbox acceptance

Identify or, after approval, create a dedicated general sandbox owned by the studio. Record its account/sandbox IDs and prove test-mode configuration. Use legitimate test instruments and owned test customer addresses; never live keys, cards or accounts. Preferred key is restricted `rk_test_…`; secret keys are server-only. [Sandbox isolation](https://docs.stripe.com/sandboxes), [key types](https://docs.stripe.com/keys).

Grant only the scenario's required resources: checkout session create/read/expire; customer create/read; product and price create/read/update where needed; subscription read/update/cancel; invoice and invoice-item create/read for renewal tests; PaymentMethod read and refunds only for the explicitly approved cases. Billing Portal session creation is needed only if tested. Validate the exact Dashboard permission names and resulting calls before granting broader access. No Connect, Treasury, live-mode or organization-wide privileges. Preserve repository API version `2026-07-29.dahlia`.

Current fixture capability detection accepts only `sk_test_`, so a restricted test key is incorrectly reported unavailable. Correct/test that detection in a separately reviewed change before using restricted-key browser acceptance; do not widen permissions just to make the fixture green. A short-lived dedicated sandbox secret key is an alternative only with explicit approval of that exception.

Webhook route is `/api/v2/stripe-webhook`. Relevant implemented events are `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired`, `invoice.paid`, `invoice.payment_failed`, `customer.subscription.updated`, `customer.subscription.deleted`, `setup_intent.succeeded`, `charge.refunded`, and `refund.updated`. Subscribe only to events exercised by the approved matrix; retain raw-body signature validation and exactly-once receipt checks. [Webhook testing](https://docs.stripe.com/webhooks).

Netlify's perimeter gate will also block unauthenticated Stripe webhook POSTs. Do **not** remove protection or silently exempt the webhook route. A proposed later test uses a sandbox Stripe CLI listener and a reviewed local relay carrying an authenticated perimeter cookie, preserving the signed raw payload. CLI 1.53.1 supports `--forward-to`, `--headers` and `--events`; keep credentials out of process arguments/logs, do not use `--live` or skip TLS verification. This forwarding arrangement is unimplemented/unverified. It proves CLI-forwarded event processing, **not direct Dashboard-to-hosted webhook delivery**. Direct ingress remains blocked pending a separately approved protected-ingress design.

### Google Calendar and email

Use an isolated Google OAuth project/client and an owned test account/calendar with no real students, contacts or production calendars. Required inventory: OAuth client ID/secret, offline refresh token, explicit calendar ID, account address, allowlisted test users and owned recipient mailboxes. Initial Calendar phase uses `calendar.events` and the needed free/busy scope, without `gmail.send`. Calendar-only tokens cannot establish Gmail delivery acceptance. [Calendar scopes](https://developers.google.com/workspace/calendar/api/auth).

The current app uses one `GOOGLE_REFRESH_TOKEN` for Calendar and Gmail. `GMAIL_ENABLED=false` is not honored by the outbox dispatch path. Provider intake can read mail/calendar, while the outbox sends using Gmail API, not configurable SMTP. Before any Gmail-capable token is configured, review a server-enforced, fail-closed test-recipient allowlist and delivery control or an explicit sink adapter. No such guard is implemented by this proposal. A capture mailbox alone cannot prevent accidental delivery to another address.

Email acceptance may use only dedicated sender and recipient accounts owned for testing, with `gmail.send`; add `gmail.readonly` only if synthetic provider-intake testing is approved. Do not request full mailbox scope. OAuth applications in Testing can have seven-day refresh-token expiry for these scopes, which must be included in recovery checks. [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes), [OAuth lifecycle](https://developers.google.com/identity/protocols/oauth2/).

No Stripe sandbox, Google OAuth consent/token or mailbox has been created or exercised in preparation. Provider acceptance remains blocked until the resources, credentials, safeguards and exact operations are approved.

Inspect existing activity and approve its freeze before attaching staging credentials. [Scheduled functions](https://docs.netlify.com/build/functions/scheduled-functions/).
