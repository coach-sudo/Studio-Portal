## Database and existing files

Migrations: `supabase/migrations/20261008203319_studio_library_resources.sql` and `supabase/migrations/20261008220659_bounded_legacy_material_snapshots.sql`.

It extends `materials`, `material_links`, and `file_assets`; adds metadata relationships, private assignment notes, collections, collection membership and immutable collection-assignment snapshots; and adds explicit grants, RLS policies, search indexes, and transactional commands. Security-definer mutation helpers live in the non-exposed `library_internal` schema and check the caller's identity and studio permissions. Read RPCs enforce RLS.

The existing route snapshot RPC and fallback reads retain only legacy script/actor records and referenced profile photos. Ordinary resources and their storage paths are retrieved through the bounded Library queries instead. Database regression assertions verify that resources remain searchable while being excluded from eager snapshots. Material notifications use a separate RLS query limited to the latest 25 assignment summaries, with no file paths, written bodies or coach notes. Legacy script/actor controls exclude ordinary resources, so the same resource does not appear in both interfaces. The shared notification badge uses the existing coach contrast correction on student routes as well.

Existing resource IDs, student ownership, paths, external URLs, actor-publication flags and lesson relationships are retained. Existing Current/Vault/Archived states are copied onto assignments. Legacy owner-only rows receive a matching assignment so they remain discoverable. File-asset references are backfilled from existing matching studio/path records. Nothing moves, deletes, overwrites or promotes existing production files into the shared catalog.

Future uploads calculate SHA-256 and reuse a matching **authorized studio + student owner + visibility** asset. Private students, studio catalog objects and public-actor uploads are separate scopes. Random legacy objects are retained; identical names never establish identity. Assigning the Shakespeare Lexicon to additional students does not enter the upload pipeline at all.

## Storage audit and consolidation

`npx tsx scripts/audit-material-storage.ts --manifest export.json` reads administrator-exported files and produces a JSON audit. A manifest entry contains `studioId`, nullable `ownerStudentId`, `visibility`, `storagePath`, `localPath`, and optional `referenceIds`.

The tool hashes actual local bytes, distinguishes versions, groups only compatible ownership/visibility scopes, and reports object counts, referenced records and confirmed duplicate bytes **within that export**. It never changes storage or database references. Physical consolidation remains deferred until all live references, permission scopes and restorable backups have been inspected, followed by a recoverable reference migration and separately authorized cleanup. No production savings estimate is claimed.

## Remaining limits and rollout

Production migration application, deployment and merge are **not performed or authorized**. The backend migration must be reviewed and applied to the intended environment before releasing the new UI. Existing actor-media/publication and current-script tools remain in the established workflow; public actor rendering continues to use existing approval rules.

Historical physical deduplication, verified production storage totals and deletion of retained unreferenced uploads are deferred to the inspected consolidation phase above. Resource text uses safe plain text; existing lesson notes retain their sanitized rich editor. Collections are limited to 100 members and assignment operations to 100 students / 1000 collection relationships per transaction; reusable resources have no total assignment cap. Extremely large catalogs still require measured database query-plan tuning; browser responses are bounded independently of catalog size.

Individual resource pickers assign one resource per action; collections provide multi-resource assignment to multiple students. The isolated Stripe checkout journey requires a Stripe test key and remains explicitly blocked/skipped when none is configured; production credentials are never used as a substitute.
